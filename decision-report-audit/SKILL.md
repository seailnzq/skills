# 决策报告审计与修订 — 五维审计 → 安全写回闭环

> 目的：把「对一份已成文的个人决策报告做技术逻辑审计，再把修正安全落回 wiki-life 仓库」焊成一条可复现流水线。校准样例见 reference.md（2026 社保参保地选择报告：北京/杭州/昆明，五维实审 + v4 情景对齐收口）。

## 适用对象

- 仓库：`C:\Users\l17405\github-repos\wiki-life`（git 仓库，分支 `master`，远端 GitHub），决策报告多在 `wiki/execution/`。
- 文件：已成文的 `.md` 决策报告（含 TL;DR/收口页、关键数字表、测算节、过程留痕区、可证伪清单等）。
- 语言：中文为主，PowerShell 5.1 + cmd 环境（注意 UTF-8/GBK 与 BOM 坑，见常见坑）。

## 触发场景

- 「从你的视角重新审视这个报告的分析逻辑、原始数据、计算方法，有没有缺漏」→ 走 Phase A 五维审计。
- 「按你的思路重新调整 / 把这几处硬伤改掉」→ 走 Phase B 修订闭环。
- 「给出一段话结论、最佳行动方案」→ 用固定收尾模板。
- 「写回 wiki-life 并 commit，提交信息用 XXX」→ 走写回+commit（需显式确认）。

## 不触发 / 边界

- 新建研究并归档入库 → `wiki-research-sync`。
- 情绪性回撤「扛不住/心神不宁」自处 → `portfolio-drawdown-narrative-audit`。
- 审计「对用户本人的画像文档」的事实性 → `user-profile-doc-fetch`。

## 五维审计尺（速查，详解见 reference.md）

| 维度 | 一句话尺子 | 典型致命表现 |
|---|---|---|
| ① 情景对齐 | 结论用的数字，与它推荐执行的方案，是不是**同一个情景**？ | 用「继续自缴13年」的数字得「选昆明省2.8万」，行动却走「养老停缴」——停缴则这笔成本根本不发生，省钱前提消失。这是全篇最大逻辑断裂。 |
| ② 假设支撑 | 关键假设是否有数据支撑、是否与报告自身其它节冲突？ | 「历史平均指数=2.0」与另一节「早期指数大概率<1」自相矛盾、无缴费明细支撑——**差额稳健，绝对水平当不了真预期**。 |
| ③ 口径一致 | 同一指标是否名义值/现值混用？旧数残留与新数打架？优势项被别处折扣抹平？ | 名义值与「折今日」混用；「差47元」残留而表内已改77；「门诊82%优势」被异地就医下浮抹平却仍当主依据。 |
| ④ 可复现性 | 关键数字有没有配套脚本？ | 仓库内**无测算脚本**→改数无法复核只能信任；应建议把测算固化为脚本入库。 |
| ⑤ 优先级排序 | 全文证据最强处，是否恰好落在真正的决策变量上？ | 养老差被正确判为噪声，唯一实体决策落在医保，偏偏医保那层证据最弱（费率待核、异地未算）——优先级反了。 |

**审计纪律**：逐条缺陷必须点名**行号 + 严重度**（致命/重要/次要），不硬圆；取不到的数（如无脚本、无明细）明确标注「不可复现/无支撑」，绝不编造代替。

## Phase A — 审计（只读，绝不改文件）

1. **定位源文件与可复现脚本**：读目标 `.md` 全文；`Glob`/`Grep` 仓库内是否存在配套测算脚本。若无，**如实报告「无可复现计算源，仅能就文本公式逻辑审计」**（维度④）。
2. **通读 + 结构识别**：标出收口页(TL;DR)、关键数字表、各测算节、过程留痕区(v1/v2/审计记录)、可证伪清单。
3. **五维逐查**：按上表对号入座，每条缺陷记 `行号 + 维度 + 严重度 + 一句因果`。
4. **输出按严重度排序的缺陷清单**：致命项先讲、讲透（引用具体行与数字），次要项合并列。收尾点出「真正决策量级在哪一处」（常与报告纠结的量级不在一个数量级，如「再干几年」的人生题 ≫ 社保差异）。
   - 到此**停止**，不擅自改文件。等用户指示是否修订、修订到什么范围。

## Phase B — 修订闭环（工作副本 → 确认 → 写回 → commit；push 另确认）

> 硬门控：**写回源文件、commit、push 各自都需用户显式指令**，不得从「审计/修订」自动外推到「提交」或「推送」。

1. **确认执行范围**：用 `AskUserQuestion`（或文字追问）让用户在「仅修正内部矛盾 / 补情景测算再改 / 整体重构」等之间选。用户往往选「修正内部矛盾，产物放 outputs 工作副本，暂不动仓库」。
2. **拷贝工作副本**（不动 git 源）：
   ```powershell
   Copy-Item -LiteralPath "<源文件>" -Destination "<outputs>\<同名文件>" -Force; if ($?) { "COPIED_OK" }
   ```
3. **Read 副本 → Edit 副本**：编辑前必须先 Read 副本（新路径需单独满足 Read 前置）。只改**收口页/关键数字表**，**过程留痕区原样保留**（历史推理有存档价值，不覆盖删除）；旧数残留按维度③统一校准。
4. **grep 校验无残留矛盾**：`Grep` 关键旧值与旧结论词（如 `选昆明`、旧差额数字）确认都已限定情景或降级标注。控制台中文可能 GBK 乱码，计数仍可信。
5. **present 工作副本**给用户对比。
6. **固定收尾输出**（见模板）：一段话结论 + 最佳行动方案 + 待核实清单。
7. **写回**（仅在用户明确说「写回/覆盖源文件」后）：`Copy-Item` 副本 → 源路径 `-Force`；git 仓库内文件豁免额外备份（可用 VCS 回退）。
8. **commit**（仅在用户明确下达且给出提交信息后）：
   ```powershell
   git add "<具体文件相对路径>"   # 逐个列具体文件，中文加引号，不用 -A
   git commit -m "<用户指定的提交信息>"
   git status --short; git log -1 --stat   # 确认仅目标文件变更、中文无乱码/BOM
   ```
9. **push 需再次单独确认**：本技能默认**不 push**。用户另行说「push」再执行；代理未开时降级直连 `git -c http.proxy="" -c https.proxy="" push`。

## 固定收尾输出模板

```
**结论（一段话）**：把纠结的量级讲清 + 情景是否错配 + 真正决策在哪一层（往往是「非钱」的几件事或更高量级的人生题）。
**最佳行动方案**：可执行的步骤序列（何时锁何地、停缴/续缴、领取地），以及执行前需确认的少量硬前提。
**唯一需诚实标注的不确定**：依赖未支撑假设的绝对量级点名；差额/方向稳健、绝对值当不了真预期。
**待核实清单**：每项=一个可去窗口/电话核实的具体问题（如某书面凭证、某本地年限、某费率、某缴费明细）。
```

## 常见坑

- **情景错配是最隐蔽的致命伤**：结论数字与执行方案分属两个互斥情景，读起来各自自洽、焊在一起才崩。审计第一优先找它。
- **别把「优势项」当主依据而不查折扣**：名义优势（门诊率、费率）常被异地/条件折扣抹平；改挂不受折扣影响的硬资格（如退休免缴资格）。
- **绝对值 vs 差额要分开定性**：两地/两方案**差额**通常稳健，**绝对水平**依赖假设（缴费指数等），不可当真实预期。
- **过程留痕区只增不删**：修订是「对齐收口」，不是「抹掉历史推翻过程」；被证伪的旧结论保留并标注，反而增值。
- **Edit 报 "File has not been read yet"**：拷贝出的副本是新路径，编辑前必须 Read 一次。
- **中文提交信息 BOM/乱码**：`git commit -m` 后用 `git log -1 --stat` 肉眼核对中文正常；首字节异常是 PowerShell 回读重编码的往返假象，以 `--stat` 显示为准。
- **PowerShell 5.1 不支持 `&&`**：用 `;` 与 `if ($?)`；文件操作用 `Copy-Item -LiteralPath`，路径含中文/空格加双引号。
- **门控外溢**：绝不在「审计」或「改工作副本」后自动 commit；也不在 commit 后自动 push。三级各等一句明确指令。

## 验证清单

- [ ] 缺陷清单每条带 行号+维度+严重度，致命项引用了具体数字
- [ ] 无脚本/无明细等不可复现项已如实标注，未编造代替
- [ ] 修订只动收口页，过程留痕区原样保留（diff 可证）
- [ ] grep 校验无旧值/旧结论残留矛盾
- [ ] 写回前用户已明确指令；仅目标文件被 git add
- [ ] commit 信息=用户指定、git log 中文正常、status 干净
- [ ] 未 push（除非用户另行明确要求）
